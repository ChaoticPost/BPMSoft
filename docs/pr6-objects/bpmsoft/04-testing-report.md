### Негативные проверки (для скриншотов «Проверки обязательности» и «уникальности»)

- [ ] Попытка сохранить запись без обязательного поля → ошибка платформы (скриншот).
- [ ] Дубликат `Code` промокода → если уникальный индекс есть, ошибка; если нет —
      зафиксировать «уникальность не обеспечена lookup'ом, требуется проверка».
- [ ] Промокод с заполненными И GameSession, И TestAttempt → ожидаемое поведение
      (блокировка или отсутствие — зафиксировать факт).
- [ ] Завершённая попытка без FinishedAt/Score/Successful — если обязательность
      настроена, ошибка; иначе зафиксировать статус инварианта.

## 5. Формулировки для «честных» статусов в отчёте

Использовать дословно, где применимо:

- «права отсутствуют» — нет доступа к конфигуратору/мастеру;
- «не удалось опубликовать: <сообщение об ошибке>»;
- «требуется серверная проверка» — ограничение не выражается low-code;
- «проектное решение не утверждено заказчиком» — смешанная покупка,
  группа теста, момент выдачи, таймаут отправки, ничья, email детей;
- «переиспользован штатный объект X» — с указанием кодов и пакета.

Непрояснённые решения (не выдавать за согласованные): смешанные покупки и
округление; единственная группа версии теста; момент выдачи
(ACCEPTED vs DELIVERED); таймаут первой отправки и повторы; правило ничьей
и баллы за угадывание чужого слова; обязательность ответов на все вопросы;
email несовершеннолетнего/родителя; право ACCOUNT_DEACTIVATE; полнота
данных о покупках для аналитики.
